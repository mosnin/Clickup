# The Operate authorization server

Operate is its own OAuth 2.1 authorization server. A client that already
speaks OAuth needs nothing from us but the discovery document; this page is
for the person wiring one up, and for whoever changes these files next.

Everything below lives in four places:

| Where | What |
| --- | --- |
| `src/app/oauth/*` | the endpoints, as Next route handlers and one page |
| `src/app/.well-known/*` | discovery |
| `src/lib/oauth-server.ts` | issuer, scopes, the discovery document, shared JSON helpers |
| `convex/oauth.ts` | every decision that touches stored state |

The split is deliberate: routes parse and answer, Convex decides. A rule that
matters (is this redirect URI registered, has this code been spent, is this
grant still alive) is enforced inside a Convex transaction, so two requests
racing cannot both win.

## Discovery

- `GET /.well-known/oauth-authorization-server` (RFC 8414)
- `GET /.well-known/openid-configuration` (the same document, byte for byte)
- `GET /.well-known/oauth-protected-resource` (RFC 9728)

The protected resource is `https://operate.to/api/mcp`, and it is the only
audience this server issues tokens for. `resource` is validated against it
exactly: same origin, same path, no query, no fragment. A token cannot be
minted for a lookalike and replayed somewhere else.

## Scopes

| Scope | What it grants |
| --- | --- |
| `openid` | a subject identifier at `/oauth/userinfo` |
| `email` | the verified primary email, and only when Clerk says it is verified |
| `operate:read` | read spaces, lists, tasks, docs, agents |
| `operate:write` | create and update work, inside the chosen agent's guardrails |

`operate:write` implies `operate:read` and `email` implies `openid`; both are
added for you rather than refused. The set is closed: an unknown scope is an
error, not something quietly dropped. It lives in two places that must agree,
`OAUTH_SCOPES` in `src/lib/oauth-server.ts` (what is advertised) and
`ALLOWED_SCOPES` in `convex/oauth.ts` (what is enforced).

## Endpoints

### `GET /oauth/authorize`

A page, not an API. An unauthenticated visitor is sent to sign in and comes
back to the same URL with its query intact.

Parameters: `response_type=code`, `client_id`, `redirect_uri`, `scope`,
`state`, `code_challenge`, `code_challenge_method=S256`, `resource`.

- `redirect_uri` must match one registered for the client **byte for byte**.
  A trailing slash, an added query parameter or a changed capital is a
  different URI and is refused. There is no fallback to a default.
- `code_challenge_method` must be `S256`. `plain` is refused, and so is a
  request that names no method: OAuth 2.1 reads an absent method as `plain`.
- The person picks which agent identity the connection will run as. The
  connection inherits that agent's workspace, role, budgets and gates, and
  only the workspace's owner may pick a workspace agent.
- On approve, the browser is sent to `redirect_uri` with `code`, the `state`
  unchanged, and `iss` (RFC 9207). On deny, the same with
  `error=access_denied` instead of a code.
- A refused request renders an error page and redirects nowhere. It names no
  parameter, so it cannot be used to probe for registered URIs.

The code is single use, lives **ten minutes**, and is bound to the client,
the redirect URI, the challenge, the resource, the agent and the person.

### `POST /oauth/token`

`application/x-www-form-urlencoded`. JSON is accepted too, for the device
grant's benefit.

Three grants: `authorization_code`, `refresh_token`, and
`urn:ietf:params:oauth:grant-type:device_code` (RFC 8628, which answers with
an agent API key rather than an access token; see `docs/AGENTS.md`).

Success is HTTP 200, `Cache-Control: no-store`, and:

```json
{
  "access_token": "opa_…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "opr_…",
  "scope": "operate:read operate:write"
}
```

Both tokens are generated by the route and only their SHA-256 digests reach
the database, so a database read does not yield a usable credential. The PKCE
challenge is compared in constant time; the verifier is checked against RFC
7636's own shape first.

Refresh tokens **rotate**: every refresh retires the token it was given and
returns a new pair.

**Replay is answered with revocation.** An authorization code presented twice,
or a rotated refresh token presented again, revokes the entire grant family
(every access and refresh token that grant ever minted) and answers HTTP 400
with `{"error": "invalid_grant"}`. Rotation without this would detect nothing:
the point of rotating is that the second use of a token proves a copy exists,
and the only safe response to a copy is to end the grant and make the person
reconnect. An ordinary failure, such as a mismatched verifier, is a plain 400
and leaves the grant alone.

### `POST /oauth/revoke`

`application/x-www-form-urlencoded` with `client_id` and `token`. Either half
of the pair may be presented; both die, along with everything else issued
under the same grant.

The answer is **200 with an empty body**, always: for a token that was never
issued, for one already revoked, and for a body that does not parse. RFC 7009
defines an unknown token as a successful revocation, and anything else would
turn this endpoint into an oracle for which tokens are live.

### `GET /oauth/userinfo`

`Authorization: Bearer <access token>`, requires `openid` and `email`.

```json
{
  "sub": "user_…",
  "email": "ana@example.com",
  "email_verified": true,
  "name": "Ana Ruiz",
  "org_id": "…",
  "org_name": "Ruiz Dental"
}
```

`email_verified` is only ever `true`, and only when the signed Clerk webhook
said so. An OAuth token is not evidence about an email address.

Operate is multi tenant, so the answer also names the workspace the token
speaks for: `org_id` and `org_name` are the workspace behind the token's
agent, which is what the grant was bound to rather than whichever workspace
the person happens to prefer. A token bound to a personal-space agent has no
organization and both claims are omitted.

### `POST /oauth/register`

RFC 7591 dynamic client registration, open and rate limited per source
address. Send `client_name` and `redirect_uris`; you get back a `client_id`
and no secret, because every client here is public and uses PKCE.

```bash
curl -sS https://operate.to/oauth/register \
  -H 'content-type: application/json' \
  -d '{"client_name":"Acme Desktop","redirect_uris":["https://acme.example/callback"]}'
```

Redirect URIs must be HTTPS, or HTTP on `localhost` / `127.0.0.1` for local
development. A confidential client (`client_secret_basic` or
`client_secret_post`) is refused rather than silently downgraded.

To register a client by hand instead, insert a row into `oauthClients` with
`clientId`, `clientName`, `redirectUris`, `tokenEndpointAuthMethod: "none"`
and `grantTypes`, or call `oauth.registerClient` from the Convex dashboard.

### `POST /oauth/device`

RFC 8628 device authorization, for runtimes with no browser. See
`docs/AGENTS.md`; it is documented there because what it issues is an agent
key rather than an OAuth token.

## Environment variables

| Variable | Read by | Used for |
| --- | --- | --- |
| `NEXT_PUBLIC_APP_URL` | Next | the issuer, every URL in the discovery document, and the canonical resource |
| `NEXT_PUBLIC_CONVEX_URL` | Next | reaching the backend that holds clients, codes and tokens |
| `DEVICE_PROXY_SECRET` | Next and Convex | proves the device endpoint reported a real client address to the rate limiter |

No client secrets exist to configure. Clients are public by design.

## Grant families

Each authorization code opens one grant, identified by a `grantId` derived
from the code. Every token minted under it, through the first exchange and
every rotation after, carries the same value, and `oauthAccessTokens` is
indexed by it. That is what makes "revoke everything this grant ever issued"
one indexed read rather than a walk, and it is the mechanism behind both
replay revocation and `/oauth/revoke`.

Rows written before `grantId` existed do not have one. They fall back to
revoking the single token presented, which is what the server did before.
